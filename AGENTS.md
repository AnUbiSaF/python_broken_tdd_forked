# AGENTS.md

Правила репозитория для LLM-агентов: opencode, Claude Code, Codex CLI, Aider,
Cursor и любые другие. Агент читает этот файл целиком до начала работы.

## Что это за проект

Учебный репозиторий. В нём две независимые части:

* **часть 1** — починка красного CI (форматирование, линт, типы, тесты) в
  `src/shop/inventory.py` и `src/shop/reporting.py`;
* **часть 2** — реализация расчёта суммы заказа в `src/shop/checkout.py`
  по ТЗ из `src/shop/specs/checkout.md`, через цикл RED → GREEN → REFACTOR.

Зелёное состояние достигается командой `./scripts/check.sh`.

## Жёсткие ограничения

1. **Не создавать классы.** Данные — это `dict`, `list`, `tuple`. Всё, что можно
   выразить функцией, выражается функцией.
2. **Не использовать `try` / `except` и `raise`.** Некорректный вход возвращается
   через `None` и ранний `return`. Тип результата — `X | None`.
3. **Не трогать `tests/`.** Ни одного символа: тесты пишет студент, агент их
   реализует. Единственное исключение — явно полученная от преподавателя просьба.
4. **Не ослаблять проверки.** Нельзя удалять или переписывать `assert`, ставить
   `pytest.mark.skip` / `xfail`, молча добавлять `# type: ignore` или `# noqa`.
   Подавление диагностики допускается только с объяснением в комментарии.
5. **Не добавлять зависимости** и не менять `pyproject.toml`. Новые инструменты —
   это отдельная задача, согласованная с преподавателем.
6. **Не менять** константы `PROMO_CODES`, `SUPPORTED_CITIES`, `MAX_DISCOUNT_PERCENT`,
   `VAT_PERCENT`, `SHIPPING_KOPEKS`, `FREE_DELIVERY_FROM_KOPEKS`, `TIER_DISCOUNTS`,
   `REQUIRED_LINE_KEYS`, сигнатуры функций из `src/shop/checkout.py` и содержимое
   `tests/test_money.py`.
7. **Не удалять существующие тесты** и не переименовывать тестовые функции.

## Стиль

* Типы указываются у всех функций, включая тесты: `-> None` у тестов.
* Деньги — целое число копеек. `float` в денежных расчётах запрещён.
* Проценты считаются целочисленно через `shop.money.percent_of`.
* Идентификаторы, комментарии и docstring-и — по-английски.
* Комментарий объясняет *почему*, а не *что*.
* Один коммит — одна тестовая и одна реализационная правка; порядок коммитов
  проверяется скриптом `scripts/check_tdd_history.py`.

## Порядок работы над частью 2

1. Студент пишет один красный тест и коммитит **только тест**.
2. Агент получает этот тест и спецификацию, реализует **минимальный** объём
   кода, который делает этот тест зелёным, и не трогает остальные тесты.
3. Студент запускает `./scripts/check-part2.sh` и убеждается, что стало зелёным,
   затем не ыыпишет следующий красный тест.
4. Рефакторинг — отдельный шаг после зелёного, коммитится отдельно.

Если задача звучит как «сделай так, чтобы тесты прошли», а часть тестов ещё
красные, — сначала спроси, какой именно тест должен стать зелёным, и реализуй
только его. Массовое «переписывание» функции под все тесты разом — это не TDD.

## Проверки перед завершением

Агент обязан прогнать и показать вывод:

```bash
./scripts/check.sh          # весь набор, ожидается полностью зелёный
```

Не «зелёный по мнению агента», а фактический вывод `pytest` без `failed`.
Если часть проверок красная по объективной причине (задание не выполнено
до конца) — сказать об этом прямо, а не описывать ситуацию как успешную.
